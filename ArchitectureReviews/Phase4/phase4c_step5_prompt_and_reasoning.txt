PHASE 4C STEP 5 — EXPLICIT MANUAL ACTIVATION OF A CONVERTED EXPERIMENT

REASONING

Phase 4C Step 4 now provides the durable boundary between an approved recommendation-conversion proposal and exactly one newly created experiment. The created experiment is deliberately paused, is not scheduler-owned, and cannot start merely because a recommendation was approved or converted.

The next safe step is to add a second, explicit operator action that activates that already-created paused experiment. This preserves the separation of duties:

1. recommendation generation and ranking remain advisory;
2. proposal preparation records conversion intent;
3. review records approval or rejection;
4. execution creates exactly one paused experiment;
5. activation is a separate, auditable decision that makes the experiment eligible for the existing scheduler.

Activation must not create another experiment, reinterpret the recommendation, or introduce recommendation-driven scheduler automation. It should reuse the existing experiment lifecycle and queueing behavior, while adding durable provenance and strong idempotency around this specific Phase 4C transition.

PROMPT FOR CODEX

Using high reasoning, implement Phase 4C Step 5: explicit manual activation of an already executed recommendation-conversion proposal.

REPOSITORY AND BRANCH

Use the current repository state on:

  branch: phase0-architecture

The branch includes Phase 4C Step 4 and its live-PostgreSQL verification. Treat the current implementation as authoritative. Do not rediscover or redesign the completed Step 2, Step 3, or Step 4 architecture.

Before editing, inspect the current Phase 4C migrations, repositories, services, CLI wiring, tests, documentation, and the existing experiment pause/resume/requeue lifecycle. Reuse established lifecycle behavior rather than duplicating it.

GOAL

Add a deliberate, explicit, durable operator action that activates the single paused experiment created by a Phase 4C conversion execution.

A successful activation must:

- operate only on an existing durable conversion-execution record;
- target exactly the experiment linked by that execution record;
- verify that the experiment is still in the precise safe pre-activation state;
- transition that existing experiment into the normal scheduler-eligible state using established experiment lifecycle semantics;
- create durable append-only activation evidence;
- be transactionally idempotent;
- prevent duplicate activation under concurrent requests;
- preserve proposal, review, execution, experiment, and activation provenance;
- never create another experiment;
- never directly launch a worker;
- never bypass the scheduler.

PHASE BOUNDARY

Step 5 remains an explicit manual administrative action.

It must not:

- automatically activate an experiment after approval;
- automatically activate an experiment after conversion;
- scan for executions to activate;
- add scheduler polling of recommendation, proposal, review, execution, or activation tables;
- start training, inference, or analysis directly;
- create a second experiment;
- mutate recommendations, ranking snapshots, proposals, reviews, or execution records;
- approve or reject proposals;
- alter recommendation scoring or ranking;
- add broad workflow orchestration;
- redesign the experiment scheduler;
- commit changes.

REQUIRED DOMAIN BEHAVIOR

Introduce a clear activation result model with outcomes such as:

- activated
- existing_identical
- not_found
- invalid_state
- conflict

Use naming consistent with the current Phase 4C code.

The durable activation identity must be deterministic and must bind at least:

- activation contract version;
- conversion execution ID;
- proposal ID;
- approving review-decision ID;
- experiment ID;
- intended lifecycle transition;
- resulting scheduler-eligible status/phase;
- any lifecycle-relevant immutable values required to prove that replay refers to the same activation.

Store both canonical activation identity and its hash, following the existing canonicalization and hash conventions.

DATABASE MIGRATION

Add the next numbered migration after 038.

Create one append-only activation table with a narrow responsibility. It should link:

- conversion execution;
- proposal;
- approving review decision where useful for direct provenance;
- experiment;
- activation contract version;
- canonical activation identity;
- activation identity hash;
- created timestamp.

Enforce database-backed invariants, including:

- exactly one activation record per conversion execution;
- exactly one activation record for the linked experiment through this workflow;
- foreign-key consistency among execution, proposal, review decision, and experiment;
- positive identifiers;
- supported contract version;
- nonempty bounded canonical/hash fields;
- restrictive deletion behavior;
- no UPDATE or DELETE privilege for the runtime role;
- no PUBLIC privileges;
- only the minimum SELECT/INSERT/sequence privileges required by the runtime role.

Prefer composite foreign keys or other database constraints where they materially prove cross-record consistency. Do not rely only on application checks for duplicate prevention or provenance.

SAFE PRE-ACTIVATION STATE

The operation must reject activation unless the linked experiment is still exactly the experiment produced by Step 4 and remains safe to activate.

At minimum, verify the current experiment is:

- status = paused;
- phase = train;
- worker_pid IS NULL;
- current_operation IS NULL;
- current_epoch IS NULL unless the existing experiment-creation contract intentionally sets it;
- not already running, pending, completed, failed, cancelled, or otherwise lifecycle-advanced;
- still consistent with the immutable proposal/execution provenance used to create it.

Also verify that the execution record itself is valid and references an approving review decision protected by the Step 4 schema.

Do not silently repair an invalid state. Return a deterministic failure with a specific reason.

ACTIVATION TRANSITION

Use the existing project-defined scheduler-eligible lifecycle transition. Do not invent a parallel queue mechanism.

Determine from the current code whether the correct existing state is:

- pending/train,
- queued/train,
- or another established equivalent.

Apply exactly the same field clearing/initialization rules used by the normal experiment resume/requeue path.

The activation operation must not spawn a process. It only makes the experiment eligible for the existing scheduler.

TRANSACTIONAL AND CONCURRENT BEHAVIOR

The activation must be atomic:

- validate execution and linked experiment;
- acquire a proposal/execution/experiment-scoped database lock suitable for the runtime role;
- insert durable activation evidence;
- transition the existing experiment;
- commit both together.

If any part fails, neither the activation row nor lifecycle transition may remain committed.

Concurrent identical activation requests must result in:

- one lifecycle transition;
- one activation row;
- all successful callers receiving the same persisted activation and experiment identity;
- no duplicate rows;
- no sequence-value assumptions.

A replay after successful activation must return existing_identical without trying to repeat the lifecycle update.

If an activation row exists but its canonical identity differs from the current deterministic identity, return conflict and do not mutate anything.

Do not require table-level UPDATE privileges merely to lock a row if that conflicts with the established restricted runtime role. Reuse the advisory-lock pattern from Step 4 when appropriate.
