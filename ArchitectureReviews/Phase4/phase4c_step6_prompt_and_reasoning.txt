PHASE 4C STEP 6 — END-TO-END CONVERSION WORKFLOW OBSERVABILITY

REASONING

Phase 4C now has the complete explicit manual mutation chain:

1. Step 2 persists a recommendation-conversion proposal.
2. Step 3 records append-only operator review decisions.
3. Step 4 executes an approved proposal by creating exactly one paused experiment.
4. Step 5 separately activates that exact experiment by moving it from paused/train to pending/train.

The current working tree contains the uncommitted Step 5 implementation. Preserve those changes. Do not reset, discard, overwrite, or commit them.

Before adding any new mutation or automation, the next safe Phase 4 step is read-only end-to-end observability. An operator should be able to inspect one proposal or one workflow and see the complete durable chain without manually joining several tables or issuing multiple commands.

This step should not alter recommendation policy, create experiments, review proposals, execute proposals, activate experiments, or affect scheduler behavior. It should provide a deterministic, machine-readable and human-readable view of:

recommendation → proposal → latest review disposition → execution → activation → experiment lifecycle

That gives us a reliable operational checkpoint before moving toward broader Phase 4 automation, campaign control, or profitability-aware selection.

WORKFLOW STATE DERIVATION

Derive workflow state deterministically from durable records.

At minimum:

- no review decision:
    pending_review

- latest review disposition reject:
    rejected

- latest review disposition approve, no execution:
    approved_not_executed

- execution exists, no activation, linked experiment remains paused/train:
    executed_paused

- activation exists, experiment remains pending/train:
    activated_pending

- activation exists and experiment is running or has worker ownership:
    scheduler_claimed_or_running

- activation exists and experiment is completed:
    completed

- activation exists and experiment is failed:
    failed

- activation exists and experiment is cancelled:
    cancelled

- any impossible or provenance-breaking combination:
    inconsistent

A proposal that exists but has no review may also be labeled proposed plus a more specific pending_review state if the project favors separate stage and state fields.

Do not infer state from timestamps when stronger IDs, foreign keys, review ordering, or lifecycle fields exist.

The greatest review-decision ID remains the authoritative latest review disposition, consistent with Step 3.

INTEGRITY DIAGNOSTICS

The read model must detect and clearly report inconsistencies instead of silently normalizing them.

Detect at least:

- execution exists but references a non-approve review;
- execution proposal ID does not match the requested proposal;
- activation provenance does not match execution;
- activation exists without execution;
- activation says paused→pending but experiment is still paused with no valid replay explanation;
- execution exists but linked experiment is missing;
- activation exists but linked experiment differs;
- stored canonical/hash mismatch detected by existing repository validation;
- multiple records where uniqueness should make only one possible;
- experiment lifecycle state incompatible with whether activation exists;
- unsupported contract versions;
- missing required schemas.

Return deterministic diagnostic codes and preserve all useful IDs in output.

Do not repair inconsistencies.
