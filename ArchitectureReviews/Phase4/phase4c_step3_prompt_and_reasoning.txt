PHASE 4C STEP 3 — MANUAL REVIEW AND APPROVAL WORKFLOW FOR DURABLE CONVERSION PROPOSALS

Use high reasoning.

- Work on the current branch and current uncommitted state only.
- Preserve all completed Phase 4A, Phase 4B, and Phase 4C Step 1–2 behavior.
- Do not interrupt, launch, resume, cancel, pause, retry, or otherwise affect any running or pending experiments.
- Do not run tests against the active LSTM production/research database.
- Any PostgreSQL integration testing must use a separate disposable database and isolated schema.

GOAL

Implement Phase 4C Step 3: a durable, explicit, manual review and approval workflow for persisted experiment recommendation conversion proposals.

Step 2 established immutable persistence for conversion proposals. Step 3 must add the durable review decision layer that records whether a human operator approved or rejected a specific persisted proposal.

This step must remain advisory and administrative. Approval must not create, queue, resume, modify, or execute an experiment.

The result must provide:

1. A durable append-only review-decision record.
2. Explicit proposal states derived from persisted decisions.
3. Deterministic duplicate/idempotency behavior.
4. Repository APIs for recording and reading decisions.
5. CLI commands for manually approving, rejecting, and inspecting proposals.
6. Tests covering schema, repository behavior, concurrency, immutability, and CLI behavior.
7. Documentation of invariants and operational boundaries.

PHASE BOUNDARY

Phase 4C Step 3 may:

- read persisted conversion proposals,
- list or inspect proposals,
- record an explicit manual approval decision,
- record an explicit manual rejection decision,
- persist optional operator notes or reason text,
- report the current review disposition of a proposal,
- expose proposal and review information through CLI commands.

Phase 4C Step 3 must not:

- create an experiment,
- insert into the experiment table,
- queue an experiment,
- modify experiment status or phase,
- launch training, inference, or analysis,
- invoke scheduler behavior,
- resume, retry, pause, cancel, or continue an experiment,
- score or rerank recommendations,
- regenerate or mutate an existing conversion proposal,
- silently approve anything,
- automatically approve based on score or policy,
- convert approval into execution,
- alter existing Phase 3 continuation behavior,
- alter the active scheduler,
- add background workers or automation.

Approval in Step 3 means only:

“An operator has durably approved this exact persisted proposal for possible conversion in a later phase.”

It does not mean:

“Create or queue the experiment now.”

DESIGN REQUIREMENTS

A. Review decisions must refer to exact persisted proposals

Each review decision must reference the durable proposal primary key created in Step 2.

Do not reconstruct proposal identity from recommendation fields at review time.

Do not approve by hash alone.

Do not approve by rank position, symbol, horizon, or recommendation ID alone.

The proposal row is the exact object under review.

B. Append-only audit history

Prefer an append-only review-decision table rather than mutable approval columns on the proposal table.

The decision table should preserve:

- review decision ID,
- proposal ID,
- decision type,
- optional reason or note,
- operator identity when supplied,
- decision timestamp,
- deterministic idempotency key or equivalent request identity if needed,
- creation timestamp.

Do not update or delete historical decisions through the runtime repository.

Do not mutate the persisted proposal row.

C. Decision model

At minimum support:

- approved
- rejected

Do not add automatic, queued, converted, executed, expired, or scheduler-related states in this step.

The current disposition should be derived deterministically from persisted history.

Recommended rule:

- no decision rows: pending_review
- latest valid decision approved: approved
- latest valid decision rejected: rejected

If the project’s architecture strongly favors one terminal decision only, evaluate that alternative carefully. However, do not silently choose a model without documenting the tradeoff.

The preferred design is to support an auditable sequence of explicit manual decisions so that a later operator may reverse an earlier decision without destroying history. If reversals are supported:

- each new decision is appended,
- the latest decision determines current disposition,
- the full decision history remains queryable,
- duplicate retries of the same request do not append duplicate rows.

D. Idempotency and duplicate semantics

Manual CLI retries must be safe.

Define a clear deterministic rule for duplicate decision requests.

A robust approach is an explicit decision request key generated or supplied by the caller and uniquely constrained per proposal. Another acceptable approach is a canonical decision identity covering proposal, disposition, normalized operator identity, normalized reason, and a caller-visible request token.

Do not make repeated identical approvals create unlimited duplicate audit rows due only to network or CLI retry.

At the same time, do not prevent a legitimate later reversal or a new deliberate decision.

Document the exact distinction between:

- retry of the same decision request,
- a new approval,
- a new rejection,
- a reversal of an earlier decision.

E. Concurrency

Two concurrent attempts to record the same idempotent decision must produce one durable decision and deterministic equivalent results.

Concurrent conflicting decisions must have a documented ordering rule.

Use PostgreSQL transactions and constraints as the authority.

Do not rely only on process-local mutexes.

Avoid race-prone “SELECT, then INSERT” behavior unless protected by a transaction-safe database mechanism.

F. Permissions and immutability

Follow the Step 2 persistence model:

- runtime role may INSERT and SELECT the review-decision table,
- runtime role must not UPDATE, DELETE, or TRUNCATE review decisions,
- runtime role must not mutate proposal identity rows,
- migration/admin ownership may retain schema-management rights.

Tests must tolerate the established libpqxx behavior where sql_error::sqlstate() may be empty for a PostgreSQL permission error. Prefer SQLSTATE 42501, with a narrowly scoped fallback that confirms the server message reports “permission denied.”

Do not weaken tests to accept arbitrary SQL errors.

G. Canonical values and validation

Use a constrained database representation for decision type.

Reject unknown decision values.

Normalize and validate optional operator and reason fields consistently.

Define size limits to prevent unbounded text storage.

Preserve user-entered reason text unless an existing project convention requires normalization.

Do not allow empty strings to create ambiguous identities where NULL is the intended representation.

H. Repository API

Add a focused repository abstraction consistent with the Step 2 repository.

Expected capabilities include equivalents of:

- recordReviewDecision(...)
- findReviewDecisionById(...)
- listReviewDecisionsForProposal(...)
- getCurrentReviewDisposition(...)
- listProposalsByReviewDisposition(...), if consistent with existing repository patterns.

The API must return enough information to distinguish:

- inserted,
- idempotent replay,
- not found,
- invalid request,
- database failure.

Do not mix CLI formatting into repository logic.

Do not add scheduler or experiment creation dependencies to the repository.

I. CLI

Add explicit manual commands consistent with current CLI conventions.

The exact naming should follow the repository’s existing style, but expected capabilities include:

- approve a persisted conversion proposal,
- reject a persisted conversion proposal,

Possible command shape, subject to repository conventions:

REASONING

Phase 4C Step 2 made conversion proposals durable and immutable, but persistence alone does not provide a safe operational workflow. Before any later phase may create experiments, the system needs an explicit human decision boundary that is durable, inspectable, idempotent, and auditable.

An append-only review-decision table is preferable to mutable approval columns because it preserves history. A mutable approved flag would lose who made the decision, why it was made, whether it was reversed, and how concurrent or repeated requests were handled. The audit record becomes especially important once later steps are allowed to convert an approved proposal into an experiment.

The proposal itself must remain immutable. A review is a statement about one exact persisted proposal, not a mutation of that proposal. Referencing the proposal primary key prevents a later review from accidentally applying to a regenerated recommendation or to a hash collision.

Approval must remain separate from execution. Combining approval with experiment creation would make it difficult to inspect, test, retry, or reverse a human decision without risking scheduler side effects. Step 3 therefore ends after durable review persistence. A later step can consume approved proposals under its own transactional safeguards and explicit operator command.

Idempotency is necessary because a CLI command may be retried after a timeout or uncertain response. Without request identity, a retry could create duplicate audit rows. At the same time, legitimate reversals must remain possible. Therefore, the implementation must distinguish replay of the same request from a new deliberate decision.

Database constraints and transactions must define concurrency behavior. Process-local synchronization is insufficient because multiple CLI processes may operate simultaneously. Identical concurrent requests should converge to one durable decision. Conflicting decisions should both remain auditable or follow another explicitly documented deterministic rule; the current disposition must never depend on unspecified row ordering.

Runtime permissions should continue the Step 2 pattern: INSERT and SELECT are allowed, while UPDATE and DELETE are denied. This makes the append-only guarantee enforceable at the database boundary rather than merely by convention. Tests should verify the actual PostgreSQL denial while remaining portable across the observed libpqxx behavior where SQLSTATE may be absent.

This step creates the durable human-governance boundary required before actual conversion. It should not yet create experiments, queue work, or involve the scheduler. Keeping that boundary strict limits regression risk and makes the later execution step easier to reason about and audit.
