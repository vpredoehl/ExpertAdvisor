PHASE 4D STEP 1 — DETERMINISTIC RECOMMENDATION CAMPAIGN PLANNING

REASONING

Phase 4C is complete and committed at:

  c2d7fef
  Implement read-only recommendation conversion workflow status and diagnostics.

Phase 4C established a complete, durable, auditable manual mutation chain:

  recommendation
  → conversion proposal
  → append-only review
  → execution to paused experiment
  → explicit activation to pending
  → ordinary scheduler lifecycle

Step 6 added read-only end-to-end workflow observability and deterministic integrity diagnostics.

The next safe Phase 4 increment should not jump directly to automatic proposal creation or automatic activation. The system first needs a deterministic campaign-planning layer that can answer:

  “Given the current ranked recommendations and existing Phase 4C workflow history, which recommendations would be selected for a bounded campaign, which would be skipped, and why?”

This is the correct bridge from single-item manual operation to larger-scale campaign control.

Phase 4D Step 1 should therefore be read-only. It should produce a reproducible campaign plan from existing recommendation/ranking/workflow data, without creating proposals, reviews, executions, activations, experiments, workers, or scheduler activity.

The plan should:

- select a bounded set of eligible recommendations;
- prevent duplicate or conflicting conversion work;
- preserve deterministic ordering;
- explain every included and excluded candidate;
- expose stable campaign-plan identity and hash;
- support machine-readable and human-readable output;
- remain entirely separate from future campaign execution.

This gives us a reviewable, testable policy boundary before any batch mutation is introduced.

GOAL

Add a read-only campaign planner that takes a bounded set of ranked experiment recommendations and determines which candidates would be included in a future conversion campaign.

The planner must not perform the campaign.

It must produce a deterministic plan containing:

- campaign-plan contract version;
- campaign-plan canonical identity;
- campaign-plan identity hash;
- plan generation timestamp for display only;
- policy/configuration snapshot;
- deterministic ordered candidate rows;
- include/exclude decision for every considered candidate;
- stable reason codes;
- relevant recommendation/ranking/workflow IDs;
- summary counts.

The campaign plan should answer:

- which recommendations are eligible;
- which recommendations are already represented by an existing proposal;
- which recommendations already have execution or activation history;
- which source experiments already have an active or completed conversion workflow;
- which candidates conflict with another selected candidate;
- which candidates are outside campaign limits;
- which candidates fail score, accuracy, neutrality, profitability, lifecycle, or integrity requirements;
- which candidates would be selected if campaign execution were later approved.

READ-ONLY BOUNDARY

Phase 4D Step 1 must be strictly observational.

It must not:

- insert, update, or delete any row;
- create a campaign database record;
- create a proposal;
- review a proposal;
- execute a proposal;
- activate an execution;
- create, queue, pause, resume, cancel, retry, or modify an experiment;
- start the scheduler;
- start a worker;
- add automatic scans;
- alter scheduler polling or selection;
- alter recommendation evaluation, scoring, or ranking;
- mutate Phase 4C workflow records;
- add triggers;
- commit changes.

No production SQL in this step may contain:

- INSERT

- SELECT ... FOR UPDATE
- advisory locks
- sequence access

CAMPAIGN POLICY

Add a versioned campaign-planning policy/configuration structure.

Use naming consistent with the existing project, such as:

  RecommendationCampaignPlanningPolicy

At minimum, support:

- enabled;
- maximum selected recommendations;
- maximum candidates considered;
- minimum leader score;
- minimum inference accuracy;
- maximum predicted neutral proportion;
- optional minimum profitability metric when available;
- optional maximum recommendations per symbol;
- optional maximum recommendations per horizon;
- optional maximum recommendations per source experiment;
- whether rejected workflows may be reconsidered;
- whether failed or cancelled converted experiments may be reconsidered;
- whether completed conversion workflows exclude future selection;
- whether inconsistent workflows are always excluded;
- deterministic tie-breaking configuration;
- contract version.

Do not invent profitability semantics if the current schema does not contain a reliable profitability metric. Inspect the existing analysis/ranking model first.

If profitability is not yet durably available:

- represent the policy field as unsupported or unset;
- emit a stable diagnostic/reason code;
- document that profitability-aware selection remains deferred;
- do not approximate profitability from accuracy.

The default policy must be conservative and disabled unless the user explicitly invokes the planning command.

DETERMINISTIC ORDERING

Selection must be deterministic.

Prefer existing ranking order when it has a durable rank and policy identity.

Otherwise derive order from stable persisted fields, for example:

1. ranking score descending;
2. inference accuracy descending;
3. leader score descending;
4. recommendation ID ascending.

Do not use timestamps as the primary tie-breaker when stable IDs exist.

The same database snapshot and same policy must produce:

- identical selected candidates;
- identical reason codes;
- identical canonical plan identity;
- identical plan hash.

PLAN IDENTITY

Add a canonical campaign-plan identity function and deterministic hash.

The canonical identity must include all inputs that affect candidate inclusion, exclusion, or order, including:

- contract version;
- ranking snapshot or invocation identity;
- policy canonical identity/hash;
- bounded candidate IDs in deterministic order;
- relevant persisted workflow identity/provenance;
- selection decisions and stable reason codes.

Do not include:

- wall-clock generation time;
- database connection details;
- process ID;
- host name;
- mutable display text.

Reuse the existing canonical escaping and hashing conventions.

CONFLICT RULES

Prevent the campaign plan from selecting logically conflicting work.

At minimum:

- do not select more than one candidate that would create the same conversion identity;
- do not select a recommendation already represented by an existing proposal unless explicit reconsideration policy permits it;
- do not select an inconsistent workflow;
- do not select multiple candidates for the same source experiment when policy limits it to one;
- enforce symbol, horizon, source-experiment, and campaign limits deterministically.

Do not silently collapse duplicates. Preserve and report every considered candidate.
