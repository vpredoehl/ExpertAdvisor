GOAL

Implement Phase 4C Step 2 as the durable persistence layer for manually prepared recommendation conversion proposals.

Phase 4C Step 1 already provides a pure deterministic function that validates supplied evidence and returns an in-memory `ProposedExperimentSpecification`.

This step must persist that proposal as an immutable, auditable conversion-proposal record.

It must not:

- create an experiment row;
- assign a runnable experiment;
- queue or schedule an experiment;
- alter experiment status or phase;
- resume, retry, cancel, pause, or continue an experiment;
- start a worker;
- expose automatic conversion;
- infer authorization from ranking;
- treat persistence as execution authorization.

The durable row is a prepared proposal only.

Phase 4C Step 2 owns durable proposal persistence and retrieval.

ARCHITECTURAL REQUIREMENTS

Preserve the existing ownership boundaries:

1. The Phase 4C Step 1 pure domain function remains the sole authority for conversion eligibility and proposal derivation.
2. The repository must not independently reinterpret authorization, ranking, mutation eligibility, or canonical identity.
3. Persistence accepts a successfully built `ProposedExperimentSpecification` and stores it faithfully.
4. Canonical conversion text is authoritative for equality.
5. The hash is only an indexed accelerator and must never be trusted without exact canonical-text comparison.
6. Ranking provenance remains optional advisory metadata and is not part of conversion identity or authorization.
7. Persisting a proposal does not authorize experiment creation or execution.
8. No scheduler component may depend on, scan, or act on these rows in this step.
9. Existing Phase 4A and Phase 4B recommendation behavior must remain unchanged.

SCHEMA REQUIREMENTS

Design a narrowly scoped table for immutable manual conversion proposals.

The exact naming should follow existing project conventions, but the persisted record must include enough information to reconstruct and audit the Step 1 proposal without consulting volatile process state.

At minimum, persist:

- proposal primary key;
- recommendation ID;
- source experiment ID;
- conversion contract version;
- changed mutation parameter;
- canonical source value;
- canonical proposed value;
- recommendation semantic hash;
- evaluation identity hash;
- evaluation policy hash;
- scoring policy hash;
- review authorization hash;
- optional ranking snapshot identity hash;
- complete proposed invocation/configuration fields required to reconstruct `ExperimentInvocationConfiguration`;
- authoritative conversion identity canonical text;
- conversion identity hash;
- creation timestamp.

Also persist canonical source/proposed invocation representations or equivalent complete structured values when needed to preserve exact auditability. Do not omit information merely because it can currently be recomputed from mutable source rows.

Constraints must enforce, where appropriate:

- positive recommendation ID;
- positive source experiment ID;
- valid contract version;
- non-empty mutation parameter;
- non-empty authoritative canonical identity;
- non-empty identity hash;
- uniqueness that prevents exact duplicate proposal persistence.

Hash uniqueness alone is insufficient. If PostgreSQL cannot directly express exact canonical duplicate semantics with the desired index design, implement safe transactional lookup plus an appropriate uniqueness constraint and document the collision handling.

Do not add foreign-key behavior that can delete proposal audit history through cascading deletion.

REPOSITORY CONTRACT

DUPLICATE AND COLLISION HANDLING

Implement exact duplicate semantics.

Required behavior:

- same authoritative canonical text: return the existing proposal deterministically;
- same hash but different canonical text: treat as a hash collision, not as a duplicate;
- concurrent same-canonical insertion: exactly one row survives;
- different recommendation or evidence provenance that changes canonical identity: create a distinct proposal;
- ranking-only changes: must not change conversion identity and therefore must not create a new logical proposal.

Add stable result types or reason codes for:

- created;
- existing identical proposal;
- hash collision or inconsistent persisted identity;
- invalid persistence input;
- repository failure, following existing project error conventions.

Do not silently collapse different canonical identities.

REASONING

Phase 4C Step 1 established the pure deterministic contract that validates a manually authorized recommendation and derives a complete in-memory `ProposedExperimentSpecification`.

The next safe increment is to persist that exact proposal as an immutable audit record without crossing into experiment creation or scheduler execution.

Durable persistence is needed before operational conversion because later steps must have:

- a stable proposal identifier;
- exact canonical duplicate detection;
- concurrency-safe idempotency;
- complete reconstruction of the proposed invocation;
- durable authorization and evidence provenance;
- an auditable separation between “proposal prepared” and “experiment created.”

Keeping this step persistence-only preserves the architecture boundary. It allows the system to remember and inspect manually prepared proposals while preventing a persisted recommendation proposal from becoming executable merely because it exists.

Experiment creation, explicit operator execution commands, transactional proposal-to-experiment conversion, queueing, budgets, and scheduler interaction remain deferred to later Phase 4C steps.
