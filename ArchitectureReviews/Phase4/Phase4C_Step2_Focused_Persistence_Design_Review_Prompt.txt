REASONING

The Phase 4C Step 2 implementation appears architecturally disciplined and remains within the intended persistence-only boundary.

The main unresolved question is not whether the feature belongs in Phase 4C, but whether the chosen duplicate and collision design is the simplest correct PostgreSQL implementation.

Canonical text is authoritative, while the application hash is only an accelerator. The persistence layer must therefore handle exact duplicates, real or synthetic hash collisions, and concurrent insertion without relying on hash uniqueness.

The current collision-ordinal design may be appropriate because PostgreSQL btree indexes cannot safely store arbitrarily large canonical text keys. However, it introduces advisory locks, bucket-local ordinal allocation, additional schema state, and more complex retry behavior.

A focused review should therefore determine whether that complexity is necessary, verify that it is fully correct under concurrency and rollback, and simplify it if a safer and more maintainable design exists.

This review intentionally excludes experiment creation, queueing, scheduler behavior, CLI orchestration, and all other later Phase 4C work.
