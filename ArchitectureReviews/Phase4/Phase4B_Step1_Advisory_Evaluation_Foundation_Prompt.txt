GOAL

Implement the first Phase 4B increment that adds a deterministic, explainable, persisted advisory evaluation layer over existing Phase 4A recommendations.

This step must remain strictly advisory.

It may evaluate, classify, score, explain, and persist recommendation evaluation evidence.

It must not approve recommendations, create experiments, queue experiments, alter experiment lifecycle state, change scheduler behavior, or interfere with running or pending work.

CURRENT PHASE BOUNDARY

Phase 4A already provides recommendation identity, candidate generation, persistence, duplicate handling, scoring/review foundations, and explicit advisory boundaries as documented in the existing Phase 4 files and Volume VIII.

Phase 4B Step 1 should introduce the evaluation foundation only.

Do not implement later Phase 4B approval, conversion, queueing, or automation behavior.

ALLOWED CAPABILITIES

This step may:

- read persisted recommendations
- read persisted recommendation scans
- read completed experiment evidence
- read inference and analysis evidence
- evaluate recommendation eligibility
- classify blocked, duplicate, stale, incomplete, or advisory-ready recommendations
- calculate deterministic score components supported by persisted evidence
- calculate a deterministic advisory total score
- generate stable explanation data
- persist evaluation runs and evaluation results
- expose explicit CLI commands for evaluation and inspection
- support dry-run evaluation
- emit stable human-readable and machine-readable output
- add additive PostgreSQL migrations
- add repository, service, domain, CLI, tests, and documentation needed for this step

FORBIDDEN CAPABILITIES

This step must not:

- approve recommendations
- reject recommendations automatically
- expire recommendations automatically
- convert recommendations into experiments
- create experiment rows
- queue experiments
- resume, retry, pause, cancel, or reprioritize experiments
- update experiment status or phase
- modify scheduler worker limits
- enter scheduler polling
- change continuation policy behavior
- change checkpoint policy behavior
- mutate model rows
- mutate inference or analysis evidence
- run training
- run inference
- run analysis
- stop or restart the scheduler
- stop or restart PostgreSQL
- signal worker processes
- alter active experiment state
- add profitability metrics that are not already persisted
- introduce opaque machine-learning-based recommendation ranking

OPERATIONAL SAFETY

Assume the scheduler and experiments may be active.

All implementation and verification must avoid interference with live work.

Do not:

- connect tests to the live LSTM database unless provably read-only
- run integration commands that queue or launch work
- hold locks on scheduler-owned experiment rows
- use SELECT FOR UPDATE on active experiment, model, inference, analysis, checkpoint, continuation, or scheduler-owned rows for advisory evaluation
- perform long-running schema changes
- run destructive migrations
- run full integration tests without first inspecting their behavior

Use isolated test schemas or disposable databases for write tests.

Use short transactions.

Prefer read-only snapshots for evidence loading.

Stable tie-breaking for any ordered output must not use insertion order.

REASONING

Phase 4B should begin by creating a trustworthy advisory evaluation foundation, not by granting execution authority.

The project already has experiment evidence, recommendation identity, persistence, duplicate handling, and a permanent architecture framework. The next safe increment is to transform persisted recommendations into deterministic, versioned, explainable evaluation evidence while preserving strict separation between recommendation analysis and experiment execution.

This step gives future ranking, approval, profitability integration, and controlled automation a reliable evidence layer. It also allows the platform to evaluate recommendations while current experiments continue uninterrupted.
