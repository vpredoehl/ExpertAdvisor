2. CURRENT DISPOSITION ORDERING

The intended rule is:

- no decisions → pending_review
- greatest review-decision primary key with approve → approved
- greatest review-decision primary key with reject → rejected

Verify that every repository and CLI query uses this rule consistently.

Check:

- no query orders only by timestamp,
- no timestamp tie can create nondeterminism,
- no caller can forge the ordering ID,
- sequences and concurrent transactions cannot create an unexpected semantic gap,
- rollback behavior does not cause an uncommitted decision to become current,
- committed rows with different request IDs remain auditable,
- the documented “latest decision wins” behavior matches actual SQL.

Evaluate whether sequence allocation order versus transaction commit order creates a semantic concern.

For example:

- Transaction A obtains decision ID 100 but commits after transaction B.
- Transaction B obtains decision ID 101 and commits first.
- Current disposition remains ID 101 even after A later commits.

Determine whether this is acceptable and correctly documented as sequence-ID order rather than commit order. If it is acceptable, explicitly confirm it. If it is not acceptable, identify the smallest safe fix without redesigning the subsystem.

REASONING

Phase 4C Step 3 creates the durable human-governance boundary that will eventually authorize later experiment conversion. That boundary must be stricter than an ordinary UI flag because it becomes audit evidence for a potentially consequential future action.

The primary risks are not limited to basic SQL correctness. They include:

- allowing runtime SQL to forge decision ordering,
- confusing sequence-allocation order with commit order,
- accepting inconsistent canonical values across C++ and PostgreSQL,
- creating duplicate audit rows during retries,
- losing deterministic behavior under concurrent requests,
- routing a supposedly advisory CLI command into scheduler behavior,
- weakening proposal immutability,
- and overstating verification when PostgreSQL tests were not executed.

The append-only model is appropriate because it preserves approvals, rejections, reversals, operator identity, reasons, and retry semantics without rewriting history. The proposal row remains the exact immutable object under review.

The request token is central to safe retries. A repeated command after a timeout must return the same durable decision rather than creating another row. At the same time, a later deliberate reversal must remain possible. Uniqueness scoped to proposal plus request ID provides that distinction, provided exact normalized payload comparison is correct.

Database constraints and privileges must be the authority. Repository conventions alone cannot prevent another runtime process from issuing raw SQL. In particular, allowing the runtime role to write the ordering primary key would undermine the “greatest decision ID wins” rule. Column-level insertion and server-generated ordering fields therefore deserve explicit review and testing.

Concurrency requires careful inspection. PostgreSQL unique-index behavior should make identical concurrent retries converge safely, but the review must verify the actual INSERT/ON CONFLICT/readback sequence. Conflicting decisions with distinct request IDs may both persist, so the resulting disposition must follow one documented deterministic order. If that order is generated decision ID rather than transaction commit order, the implementation and documentation must say so precisely.

CLI safety matters because ExperimentScheduler.cpp is the central executable entry point. Adding review commands there is acceptable only if standalone command counting, validation, and dispatch prevent review actions from mixing with scheduler or experiment-control operations.

Finally, the implementation transcript reported environmental blockers for PostgreSQL and a final Metal rebuild. Those are not necessarily code defects, but they leave important behavior unverified. This review must distinguish source correctness from environment limitations and provide exact local commands for closing any remaining verification gap before commit.
