REASONING

The focused independent Phase 6D review completed successfully and found one
blocking architectural defect:

Phase 6C already records one immutable approved/rejected administrative review
for one exact persisted Phase 6B follow-up proposal. The initial Phase 6D
implementation then records another immutable administrative approval of the
Phase 6C approved review, but it does not define a materially different
governance question, role, policy, threshold, separation-of-duty rule, or
consequence.

The implementation mechanics were otherwise judged strong:

- immutable and deterministic domain identity;
- complete Phase 6C/6B/6A provenance binding;
- approved-only eligibility;
- append-only persistence;
- transactional and concurrency-safe replay/conflict behavior;
- canonical-first equality and collision safety;
- least-privilege migration and ACL behavior;
- safe trigger context;
- typed service boundary;
- absence of activation, execution, scheduling, scheduler, worker, experiment,
  model, continuation, profitability, or campaign-success authority;
- comprehensive focused and regression tests.

The correction should therefore preserve the sound mechanics but replace the
semantically duplicative Phase 6D "approval" concept with one explicitly
distinct governance authority.

The preferred narrow correction is Phase 6D RATIFICATION:

Phase 6C asks:

    Is this proposal acceptable on its merits for possible advancement?

Phase 6D asks:

    Given the exact approved Phase 6C review and complete provenance, does an
    authorized governance actor ratify this proposal for entry into the next
    separately controlled phase?

Ratification remains immutable administrative governance evidence only. It does
not activate, execute, authorize follow-up execution, queue, schedule, signal
the scheduler, launch workers, or create/modify experiments or models.

The correction must determine and encode an explicit separation-of-duties
policy. The strongest default is:

    Phase 6D ratifier identity must differ from the Phase 6C reviewer identity.

If the repository contains an authoritative contrary policy, Codex may follow
it, but it must explain the evidence. It must not silently allow
self-ratification merely because the previous implementation did.

Because all current Phase 6D work is still uncommitted, this is the correct time
to rename the implementation comprehensively rather than preserving misleading
approval names for compatibility. No migration 044 has been committed or
deployed, so migration 044 may be rewritten or renamed within the uncommitted
change set.

The independent review also added two useful test hardenings that must be
preserved:

- fixed golden identity hash, valid UTF-8, and DEL rejection coverage;
- forced NULL-ACL fallback checks for functions, tables, and sequences using
  lowercase sequence object type `s`.

The full incremental Release build was deferred because nine training workers
were active. The correction pass should run it only if current resource load is
safe; otherwise leave it as an explicit verification gap.

This is a correction pass, not a redesign of Phase 6 and not an implementation
of Phase 6E.
